## Prompts Presets

### `browser-instructions`
Rules for web interaction using agent-browser CLI with snapshots and batching

Rules (4):
- **[BROWSER-001]** Use agent-browser for all web page interaction. Do not attempt to parse HTML manually or use wget for interactive pages.
- **[BROWSER-002]** Always take a snapshot with agent-browser snapshot -i before clicking or interacting with elements. Use the snapshot to identify correct element selectors.
- **[BROWSER-003]** Use agent-browser batch to combine two or more sequential commands into a single call, reducing round-trips.
- **[BROWSER-004]** Prefer curl and jq for API endpoints and structured data. Only use agent-browser for pages that require JavaScript rendering or interactive elements.

### `code-execution`
Guidelines for choosing bash vs python and handling scripts and packages

Rules (4):
- **[EXEC-001]** Use bash for file operations, git commands, CLI tool invocations, and simple text processing.
- **[EXEC-002]** Use python3 for data processing, complex logic, API calls, JSON/CSV manipulation, and anything requiring error handling beyond simple conditionals.
- **[EXEC-003]** Install Python packages using uv pip install. Do not use pip directly.
- **[EXEC-004]** For operations longer than ~20 lines, write the code to a file and execute it. Do not inline large scripts.

### `code-quality`
Code style consistency, linting, testing, and cleanliness standards

Rules (4):
- **[CQ-001]** Follow the existing code style of the project. Match indentation, naming conventions, import ordering, and patterns already in use.
- **[CQ-002]** Run the project's linter and formatter before committing. Fix all warnings and errors.
- **[CQ-003]** Run the test suite after making changes. All existing tests must pass before committing.
- **[CQ-004]** Never commit commented-out code. Remove dead code. Use version control to recover old code if needed.

### `debugging-workflow`
Systematic debugging workflow: reproduce, narrow down, document, report

Rules (4):
- **[DBG-001]** Always reproduce the bug reliably before attempting to diagnose or fix it. Capture exact steps, inputs, and environment.
- **[DBG-002]** Narrow down the root cause methodically. Use binary search on commits (git bisect), strace/ltrace for syscall-level issues, gdb for crashes, and log-level increases for application bugs.
- **[DBG-003]** Document findings with evidence: log snippets, stack traces, strace output, bisect results. Never say 'it seems like' without supporting data.
- **[DBG-004]** Write a debugging report with: (1) symptom, (2) reproduction steps, (3) root cause with evidence, (4) fix applied or recommended, (5) verification that the fix resolves the issue.

### `explore-tools`
Rules for discovering and using CLI tools via the explore-tools registry

Rules (3):
- **[TOOLS-001]** Before using an unfamiliar tool, run 'explore-tools show <tool>' to read its documentation and examples.
- **[TOOLS-002]** Use 'explore-tools suggest' to find the right tool for a task. Use 'explore-tools search' for keyword lookups. Use 'explore-tools ask' for complex questions.
- **[TOOLS-003]** Use 'explore-tools list' to browse all available tools by category before starting a task.

### `git-workflow`
Git branching, commit hygiene, and history-aware change workflow

Rules (4):
- **[GIT-001]** Always work on feature branches. Never commit directly to main or master.
- **[GIT-002]** Commit messages must explain WHY the change was made, not just WHAT changed. Use imperative mood in the subject line.
- **[GIT-003]** Before modifying code, run git blame and git log on the file to understand the history and intent behind existing code.
- **[GIT-004]** Keep commits atomic. Each commit should represent one logical change that passes tests independently.

### `github-pr-workflow`
Issue-driven pull request workflow using the gh CLI

- **[PR-002]** One feature or fix per pull request. Do not bundle unrelated changes.
- **[PR-003]** Link the PR to its issue using 'Closes #N' or 'Fixes #N' in the PR body so the issue auto-closes on merge.
- **[PR-004]** Include test coverage for the change. If tests cannot be added, explain why in the PR body.
- **[PR-005]** Write a descriptive PR title (under 70 chars) and body with Summary, Test Plan, and any breaking changes.

### `security-scan-workflow`
Multi-tool security scanning workflow with severity-based reporting

Rules (5):
